# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Repo in active use | Repo facts: `archived:` flag, `last push to any branch`, `latest release` | `archived` is `no`, AND `last push to any branch` is within 90 days of the bundle's capture date (eval mode) or today (live mode). A recent release is supporting evidence but not required on its own. | required |
| Maintainer is alive | Repo facts: `last 5 default-branch commits` (dates + authors) and `maintainer first-response sample` | At least one of: (a) one of the last 5 default-branch commits is authored or merged by a named human (not solely `[bot]` accounts) within 90 days of capture/today, or (b) the maintainer first-response sample shows at least one Owner/Member/Collaborator reply within 30 days of that sampled issue's opening. | required |
| Scope is one settled, bounded task | The issue body, its labels, and the comment thread | This check asks only "is this one PR's worth of work," never "is this small" or "does it touch only one file." Fail ONLY if one of these five concrete signals is present — do not fail on a general impression that the body is long, that it lists several steps, or that it touches several files: (1) the body itself literally lists *other GitHub issue numbers* (`#1234` style references to separate issues) as the units of work, or says "tracking issue"/"megaissue"/"umbrella"; (2) it is a pure usage/support question ("how do I get X to work") with no code or doc change requested; (3) a maintainer comment in the thread says the design is still undecided, unsettled, or needs discussion, and no later maintainer comment settles it; (4) the issue body itself contains an open design marker like "TBD," "if needed," or lists unresolved alternatives, with zero maintainer engagement in the thread; (5) the issue has been open 1+ year AND carries 2 or more `closed` (not merged, not open) linked PRs. Two patterns that always PASS, stated explicitly because they are easy to misread as fails: a bug report that names two or three root causes and suggests several possible implementation steps (that is one bounded bug with a diagnosis, not several tasks); and a docs or cleanup change that touches multiple pages/files to stay consistent, such as "add one new page, then update three other pages that pointed at the old approach" (that is one bounded content change, not an umbrella, as long as no other issue numbers are involved and one person doing all of it in one PR makes sense). | required |
| Nobody is already on it | Repo facts: `this issue: assignees:` and `linked PRs:` (with state), plus claim comments in the Comments section | Fails if any of: an assignee is set; any linked PR for this issue is `open` or `merged`; or a claim comment ("I'll take this," "working on this," "can I work on this," `@zulipbot claim`, etc.) was posted within 60 days of capture/today and no maintainer has since said the issue is open again. A single stale claim comment (60+ days old) with no other activity does not fail this check. | required |
| Contribution policy allows AI-assisted work | Repo facts: `contribution policy` line (CONTRIBUTING.md / AI_POLICY.md / templates) | Fails only on an outright ban on AI-generated contributions (e.g., "we do not accept AI-generated code"). Conditions — disclosure, requirements to personally understand/test/explain changes, human-review requirements — pass. No stated policy passes ("silence passes"). An `AGENTS.md` file is a positive signal, not a fail. | required |
| Maintainer responds quickly | Repo facts: `maintainer first-response sample` | At least one sampled issue got an Owner/Member/Collaborator reply within 5 days of opening. | preferred |
| Carries a beginner-friendly label | The issue's labels | Labels include something like `good first issue`, `help wanted`, or `easy`. | preferred |

## Verdict rule

Accept if and only if every `required` check passes. A single `required` check graded `fail` rejects the issue, regardless of how the others graded. `preferred` checks never change the verdict; they only order the issues the rubric already accepted (higher preferred-pass count ranks first; on a tie, prefer the issue with the more recent maintainer activity).

`unclear` is treated as `fail` for every required check: if the evidence a check needs is genuinely not in the bundle (or not findable live), the issue is not verifiably safe to take, so it does not clear that check. The one exception is the contribution-policy check, where "no stated policy" is itself a pass (silence passes) — that is a `pass`, not an `unclear`.
